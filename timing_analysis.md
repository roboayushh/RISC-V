# Single-cycle timing analysis

## Scope and method

The complete `rv32i_core` was linted with Verilator and synthesized with Yosys.
`synthesize.sh` generates the gate-level netlist and reports generic mapped
logic depth with Yosys `ltp`. These logic levels identify relative path risk;
they are not nanosecond delays because this project has no target standard-cell
or FPGA timing library and no placed-and-routed implementation.

## Long combinational paths

The architectural register-to-register paths are:

| Instruction class | Combinational path between clock edges | Timing risk |
|---|---|---|
| `LW` | PC/ROM and decode -> register-file read -> immediate mux -> ALU address add -> asynchronous data-memory read -> write-back mux -> register-file D | Highest |
| `BEQ`/`BNE` | PC/ROM and decode -> two register-file reads -> ALU subtract/zero comparison -> branch decision -> next-PC mux -> PC D | High |
| `SW` | PC/ROM and decode -> register-file reads -> immediate mux -> ALU address add -> data-memory address/data/write-enable | High |
| R-type/`ADDI` | PC/ROM and decode -> register-file read -> operand mux -> ALU -> write-back -> register-file D | Medium |
| Sequential PC | PC Q -> `PC + 4` -> next-PC mux -> PC D | Low |

Separate generic synthesis of the combinational blocks reports the ALU and
branch-target adders as the deepest individual logic cones. The load path is
still the system-level critical-path candidate because it chains a register
file read mux, ALU address calculation, a 256-word asynchronous memory read
mux, and the write-back mux in one cycle. Exact logic-level counts are recorded
in `synthesis_report.txt` and regenerated by `./synthesize.sh`.

## Load critical path

For `LW`, the clock period must cover all of the following in the same cycle:

1. Instruction ROM access and decoding of `rs1`, the I-immediate, and controls.
2. Asynchronous register-file read of the base register.
3. Sign extension and ALU-B mux selection.
4. The 32-bit address addition (`base + offset`).
5. Alignment/range checks and asynchronous data-memory word selection.
6. The memory/ALU write-back mux and register-file setup time.

The RTL models the register file and data memory with asynchronous reads. In a
generic Yosys flow, the 32x32 register file and 256x32 data memory become
flip-flops plus large mux trees. This is intentionally portable for simulation,
but it is expensive and slow compared with target-specific RAM macros. A
synchronous block RAM would add a cycle to `LW`, so using it requires a
multi-cycle or pipelined datapath rather than this single-cycle interface.

## Resource interpretation

The generic result is dominated by 9,216 enabled data flip-flops: 8,192 bits
for data memory and 1,024 bits for the register file. The PC adds 32 resettable
flip-flops. Mux cells dominate the combinational count because both storage
arrays have asynchronous read ports. The exact Yosys totals and cell-type
breakdown are in `synthesis_report.txt`.

These counts are an upper-bound implementation model, not a prediction of FPGA
LUT/BRAM use or ASIC area. A target flow should map instruction memory, data
memory, and preferably the register file to technology-specific memories.

## Single-cycle timing limitation

Every supported instruction has CPI=1, so the global clock period must be long
enough for the slowest instruction, normally `LW`. Faster operations such as
`AND` or `OR` receive no shorter cycle. Consequently, increasing memory depth,
using slower memory, or adding instructions with deeper execute logic reduces
the maximum clock frequency for the entire processor.

For a production target, the next steps are to choose a cell/FPGA library, add
clock and I/O constraints, infer or instantiate RAMs, and run post-place-route
static timing analysis. To improve frequency structurally, split fetch,
decode, execute, memory, and write-back across multiple cycles or pipeline
registers (quantified in [`docs/comparison.md`](docs/comparison.md)).

## Estimated maximum operating frequency

A silicon-accurate Fmax needs a target library and placed-and-routed timing, but
the committed logic-depth report supports a transparent first-order estimate.
Summing the measured per-block depths along the `LW` critical path (from
`synthesis_report.txt`: register-file read 10 + operand mux 1 + ALU add 69 +
data-memory read 9 + write-back mux 1) gives a datapath critical path of
**≈ 90 generic gate levels**, of which the 32-bit ripple-carry ALU is ≈ 77 %.

Estimating Fmax as `1 / (depth × t_level)` for a representative per-level delay
`t_level` (a 2-input gate plus local routing, ≈ 0.08–0.16 ns in a mature
sub-micron standard-cell process):

| t_level | Critical path (90 levels) | Estimated Fmax |
|---:|---:|---:|
| 0.08 ns | 7.2 ns | ≈ 140 MHz |
| 0.12 ns | 10.8 ns | ≈ 93 MHz |
| 0.16 ns | 14.4 ns | ≈ 69 MHz |

**Headline: ≈ 70–140 MHz (generic estimate, not timing closure.)** On a 7-series
FPGA the ripple-carry adder maps to the dedicated carry chain rather than 69 LUT
levels, so a real FPGA Fmax is usually set by the memory-read path and tends to
be higher than this conservative estimate.

For the authoritative vendor number, run the Vivado flow in
[`docs/synthesis.md`](docs/synthesis.md#authoritative-fmax-vivado-flow):
`synth_design` → `create_clock` → `place_design`/`route_design` →
`report_timing_summary`, then `Fmax = 1 / (T_target − WNS)`.
